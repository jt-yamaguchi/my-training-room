## 1. 機能要件

### F-1 会議室マスタ管理

| # | 内容 | 対応要求 |
|---|---|---|
| F-1-1 | 会議室を登録できる。項目: 会議室名(必須・50文字以内・重複不可)、定員(必須・1以上の整数)、備考(任意・200文字以内。例: 「モニタあり」) | R-1 |
| F-1-2 | 会議室の一覧を表示できる | R-1 |
| F-1-3 | 会議室の情報を編集できる | R-1 |
| F-1-4 | 会議室を削除できる。ただし**未来の予約が存在する会議室は削除できない**(予約者が困らないようにするため) | R-1, R-2 |

### F-2 予約登録

| # | 内容 | 対応要求 |
|---|---|---|
| F-2-1 | 会議室・日付・開始時刻・終了時刻を指定して予約を登録できる。項目: 件名(必須・100文字以内)、予約者名(必須・50文字以内) | R-2 |
| F-2-2 | 終了時刻は開始時刻より後であること。違反はエラーメッセージで登録を拒否する | R-2 |
| F-2-3 | **同じ会議室で時間帯の重なる予約は登録できない**。エラーメッセージで既存予約と重なっている旨を伝える | R-4 |
| F-2-4 | 過去の日時に対する新規予約は登録できない | R-2 |
| F-2-5 | 予約を取り消し(削除)できる | R-5 |

### F-3 予約照会

| # | 内容 | 対応要求 |
|---|---|---|
| F-3-1 | 日付を指定すると、その日の全会議室の予約状況を一覧表示できる | R-3 |
| F-3-2 | 会議室を選ぶと、その会議室の予約を日時順に一覧表示できる(件名・予約者名・開始/終了) | R-3 |

### 入力チェック(共通)

- 必須・文字数・数値範囲の違反は登録せず、エラーメッセージを表示する(タスク管理と同じ方式)

## 2. 非機能要件

タスク管理アプリと同一基盤のため、非機能要件は [../../design/task/02_要件定義.md](../../design/task/02_要件定義.md) の「2. 非機能要件」を踏襲する。追加事項は以下のみ。

| 分類 | 要件 |
|---|---|
| 整合性 | 同一会議室・同一時間帯に確定済みの予約が2件以上存在する状態が発生しないこと |

## 3. 制約事項

- アーキテクチャ・規約は CLAUDE.md / architecture-guide.md に従う(お手本は training-task)
- 画面はタスク管理と同様のシンプルなUIでよい(デザイン性は評価対象外)

## 4. 基本設計に委ねる論点(設計判断が必要な箇所)

以下は要件では決めない。**基本設計で方式を選び、理由とトレードオフを記載すること。**

| 論点 | 選択肢の例 |
|---|---|
| 時間帯の重複判定 | 判定ロジックの置き場所と、境界の扱い(前の予約の終了時刻=次の予約の開始時刻は重複か)。同時登録時の整合性への考え方も一言 |
| 予約時間の単位 | (a) 任意の時刻を許す / (b) 15分・30分単位に丸める。入力UIとの関係も含めて判断する |
| 日時の持ち方 | 日付+開始/終了時刻で持つか、開始/終了の日時(タイムスタンプ)で持つか。日をまたぐ予約を許すかも決める |
| 画面の分け方 | 空き状況の見せ方(日別の一覧か、会議室別か、両方か)と画面数 |

## 5. 受入基準(抜粋)

- 会議室「A会議室」(定員6)を登録 → 明日の10:00〜11:00で予約を登録できる
- 同じ会議室の10:30〜11:30の予約はエラーになり、予約は増えない
- 同じ会議室の11:00〜12:00の予約は(境界の設計判断に従い)基本設計に書いたとおりの挙動になる
- 別の会議室なら10:30〜11:30でも登録できる
- 予約を取り消すと、その時間帯に再び予約できる
- 未来の予約がある会議室の削除はエラーになる
- CI(テスト + Checkstyle + ArchUnit)が緑である

## 6. 発展要件(必須ではない。早く終わった人向け)

- 週表示(1週間×全会議室のマトリクス表示)
- 予約者名でのキーワード検索
- 利用実績の集計(会議室ごとの月間利用時間)
